# VECTIS Knowledge Transfer to Spectral Core

## Purpose

VECTIS is not only a language project. It is the reference case for how Spectral Core should turn an idea into a product that can be inspected, tested, packaged, and released.

## Architecture

Use a visible pipeline. Keep representation changes explicit. Separate parsing, validation, planning, execution, and effects.

## Security

Authority should have a name and a boundary. Filesystem, process, and network access are separate concerns. A language runtime should not gain ambient host authority.

## Product structure

Keep the public repository focused on the product. Internal orchestration and build history can exist, but they should live outside the public product tree when they do not serve the user.

## Developer experience

A serious tool needs more than a parser. It needs help, version information, environment diagnostics, formatting, inspection, project scaffolding, tests, examples, and a demonstration path.

## Documentation

Documentation is part of the contract. Specifications describe what is valid. Architecture documents describe how the system works. User guides describe how to use it. Release records describe what shipped.

## Quality

One repeatable quality gate is more valuable than several disconnected checks. The gate should cover tests, imports, repository boundaries, packaging assumptions, branding, and security policy.

## Spectral Core adoption

New Spectral Core projects should begin with the standards in this directory, then tailor only the project specific architecture and product decisions.

VECTIS remains the reference implementation. Improvements discovered in other Spectral Core projects should return to these standards when they generalize across the team.
